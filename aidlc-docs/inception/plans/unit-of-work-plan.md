## 배경: 이미 정해진 것

Application Design에서 컴포넌트(C1~C9)와 UOW 매핑이 이미 도출되어 있다. 본 단계는 그 UOW를
**정식 단위로 확정**하고, ① 단위 정의·책임, ② 의존성 매트릭스, ③ 스토리↔단위 매핑,
④ **병렬 개발 전략(사용자 요청)** 을 산출한다.

기존 UOW 초안(설계 기준):
| UOW | 이름 | 핵심 컴포넌트 | 성격 |
|---|---|---|---|
| UOW-00 | 데모 데이터셋 | `demo/` (코드 아님) | 독립 (의존 없음) |
| UOW-01 | 스캐너 & 파서 | C2(scan/parse), C7 | 기반(엔진 진입) |
| UOW-02 | Feature & Knowledge 생성 | C3(identify/generate) + C4 | AI 파이프라인 |
| UOW-03 | Claims/Evidence/Conflict | C3(extract/group/confidence) + C5 | AI 파이프라인 |
| UOW-04 | Task Impact Analysis | C6 + C3(analyze_task) | AI, 지식 소비 |
| UOW-05 | MCP 서버 인터페이스 | C1(+S1~S3 배선) | 얇은 어댑터 |
| UOW-06 | 통합·신뢰성·시연 | 횡단(모든 것) | 수렴 단계 |

## 병렬화 분석 (사용자 제약 반영)

**핵심 관찰 — 병렬화의 "이음새(seam)"는 공유 계약이다.**
C4(도메인 모델), 공통 Result envelope, C7(config), C8(프롬프트 로더), 그리고 6개 코어 함수
시그니처(component-methods.md에 이미 정의됨)를 **먼저 동결**하면 여러 트랙이 이 계약에 기대어
병렬로 진행할 수 있다.

**의존 사슬(병렬화 불가한 부분):**
- UOW-04(Impact)는 UOW-02/03의 실제 지식·충돌 산출을 소비 → 이들 이후 수렴.
- UOW-02 ↔ UOW-03은 매우 밀결합(지식 뷰가 claims/evidence/conflict를 그대로 포함) →
  둘 사이에 딱딱한 내부 이음새가 있어 **분리 병렬(2인 동시)은 코디네이션 비용이 이득보다 큼**.
- UOW-06은 전체 통합 → 마지막.

**병렬화 이득이 분명한 부분:**
- UOW-00(데모 데이터)·UOW-01(스캐너)·UOW-05(MCP 어댑터, 계약 대비 스텁으로 선개발)은
  공유 계약만 있으면 서로 독립.

이 분석을 바탕으로 아래 **권장 3-웨이브 계획**(웨이브당 최대 4트랙)을 제안한다.

## 결정 질문 (권장안 프리필)

### Q1. 공유 계약(Foundation) 단위를 신설할까?
C4 도메인 모델 + 직렬화 스키마(YAML Front Matter) + 공통 Result envelope + C7 config +
C8 프롬프트 로더 + LLMService(S4) 스켈레톤을 **UOW-0F(Foundation)** 로 묶어 **가장 먼저** 만든다.
이것이 이후 병렬 트랙의 이음새(계약)를 제공한다.

- **A. 신설한다 (권장)** — 병렬화의 전제. 계약을 한 번에 동결해 트랙 간 충돌·재작업 최소화.
- **B. 신설 안 함** — 설계대로 C4를 UOW-02 안에 두고 순차 진행(병렬 이득 축소).

**[Answer]: A**

### Q2. UOW-02와 UOW-03을 어떻게 다룰까?
둘은 하나의 AI 파이프라인으로 밀결합되어 있다.

- **A. 단위는 분리 유지하되 같은 트랙/담당(순차 02→03) (권장)** — 설계 추적성 유지 +
  밀결합 이음새 churn 방지. 병렬 2인으로 쪼개지 않음(불필요한 병렬 지양).
- **B. UOW-02+03을 한 단위로 병합** — 경계가 사실상 하나라면 병합해 관리 단순화.
- **C. 분리 + 2인 동시 병렬** — 속도는 빠르나 공유 상태(C4/C3) 충돌 비용 큼(비권장).

**[Answer]: A**

```text

  · 트랙B: UOW-02 → UOW-03 AI 파이프라인 (C3/C4/C5)     — 크리티컬 패스(단일 담당, Q2=A)
```
